# アクセスカウンター調査・修正報告（3.31.49）

調査日：2026-10-09。修正はローカル作業ツリーのみ。本番公開・コミット・push・Release作成は未実施。

## 確認できた原因と根拠

3.31.48の `docs/js/visitor-counter.js` は取得成功と番号保存の後にだけ `region.hidden = false` を実行していました。ネットワーク・HTTP・JSONエラーや4秒タイムアウトはcatchで警告を出すだけです。再試行はなく、そのページでは最後まで非表示になります。localStorageもsessionStorageも使えないと `if (!stored) return` で通信自体を行いません。取得後に両ストレージへの保存が失敗した場合もcatchに入り、受信できた数字まで表示されません。これらはモックで再現できる確定したコード上の欠陥です。

初回はhit、保存済み番号があればgetです。従来はhit応答が不明なときに記録が残らず、次回読み込みで再hitする可能性がありました。通信失敗はサーバーの加算失敗を意味しません。

HTMLの初期hiddenとCSSの間に矛盾はありません。CSSは非表示を強制せず、成功後のhidden解除で表示できます。ページ末尾の独立したmoduleスクリプトはDOM解析後に実行され、ゲーム起動側はカウンターをawaitしません。ゲーム中は親の起動画面が非表示となります。

調査したリポジトリにはService Workerの登録、カウンターを制限するCSP、Cookieへの依存がありません。ローカルWindowsサーバーはno-store/no-cacheで配信します。公開サイトの応答にはCSPがなく、HTMLは `Cache-Control: max-age=600`、カウンターURLは3.31.48でした。旧HTMLを最大10分使用し得るので、更新URLだけで即時反映を保証できません。

## 外部通信の事実と未確認事項

- 実際のGET `/api/v1/get/soundtabletennis-com-total-visitors` はHTTP 200、JSON `{ "key": "soundtabletennis-com-total-visitors", "value": 63 }` を返しました。Origin指定時の `Access-Control-Allow-Origin` は `https://soundtabletennis.com`、`Vary: Origin` でした。
- Windowsの実Chromeから同じOrigin・既存fetchオプションでGETし、200／値63／約2.7秒を確認しました。診断用の最小HTMLをローカルから同Originにモック配信し、APIのGETだけは実通信です。本番ページの全動作を確認した検査ではありません。
- JSONのvalueは既存の正整数検証に一致します。モックでは数値／数字文字列・不正値・JSON解析失敗も検証します。
- 今回のGETは4秒以内でした。4秒が症状の直接原因だった、CORSで遮断された、AndroidとWindowsの差がストレージだったとは断定できません。症状発生時のDevTools記録、実機の保存制限・拡張機能・DNS/プロキシ・旧キャッシュ、hit固有の応答時間／CORS／HTTP状態は未確認です。同一LANでもブラウザの保存状態や制限は同一とは限りません。
- 本番hitは実行していません。APIキー変更、カウント削除、初期化、外部サービス移行はありません。

## 修正と計数の方針

- 初期化時に領域と読み込み状態を表示。取得失敗も文章で表示し、10秒の期限と1.5秒／4秒の待ち時間で最大2回だけ再試行します。再試行は必ずGETです。全てタイムアウトした場合の終了目安は最大35.5秒で、ゲーム処理は待ちません。
- 既存番号があればGET。番号がなく、試行記録もなく、保存可能な場合だけ、`sttVisitorHitAttempted=1` を保存してからhitします。可能な保存先にも試行記録を複製し、再訪問でlocalStorageが制限されてもsessionStorageから検知します。同ページの重複初期化は同じPromiseを共有します。
- 失敗／中断／不正応答でhit成否が不明でも記録を維持し、再読み込みでもGETだけを使用します。個人番号が不明なら総数から推定せず、その旨と取得できた総数を表示します。
- 保存済み `sttVisitorNumber` は削除・置換せず、正常な初回hitで得た番号だけ保存します。応答後の保存不可でもそのページでは受信した番号を表示します。
- 両ストレージ不可ならGETのみ。localStorage不可ならsessionStorageを使い、同じタブのセッション中の重複を防止します。Cookieは追加しません。
- 数字はテキストとして日本語の桁区切りで表示。名前付き領域を見出し直後に維持し、aria-live、alert/statusロール、フォーカス操作、ゲーム通知への書き込みは追加しません。

## 残存する制約

外部API停止やCORS制限をクライアント修正で解消することはできません。その場合は状態表示と限定再取得になります。hit未到達でも試行記録を残すため、過少計数が起こり得ます。重複加算を避ける方針です。番号が不明なままのブラウザは自動で番号を再発行しません。

複数タブの同時初訪問にはストレージ操作とhitの間の競合が残ります。ストレージ削除、sessionStorageのセッション終了、別Origin・ブラウザ・端末の同一人物も新規扱いになり得ます。APIに冪等な訪問者識別機構がない現行方式で完全な人数の正確性は保証しません。保存領域全体を手動削除すると再加算され得るので、検証時には消さないでください。

## Windows・Android・スクリーンリーダーでの確認手順

1. 公開前はPlaywrightの `tests/visitor-counter-browser.cjs` で公開OriginとAPIをモックし、ローカルHTMLを検査します。localhostのstt.exeは従来のホスト制限によりカウンター非表示です。実サイトの確認はユーザーの公開後に行います。
2. Windows Chromeで修正版を開き、DevToolsのNetworkでHTMLと `visitor-counter.js?v=3.31.49` を確認。キャッシュ無効化／強制再読み込みを使い、ストレージを削除しないでください。Android Chromeでは必要に応じてUSBリモートデバッグで同じURL・通信・保存状態を確認します。
3. 正常時の総数と保存済み番号を確認。再読み込みではGETだけが送信されることを確認。新規ブラウザの本番確認は通常アクセスとして1回に限定し、検証目的で保存データを繰り返し消してhitしないでください。
4. DevToolsでAPIをブロックして読み込み／失敗状態を確認。最初の失敗後にブロックを解除すると、1.5秒・4秒の限定GET再試行で復帰します。全3回失敗後は再読み込みでGET再取得を確認します。番号未取得のケースは本番hitを繰り返さずモックで確認してください。
5. Windows＋NVDA、Android＋TalkBack、iPhone/macOS＋VoiceOverで、起動画面の見出しの直後に「訪問者情報」、総数、番号または取得不可の説明を順に読めることを確認。取得／再試行完了時に自動通知されず、現在のフォーカスが動かないことを確認します。数字の発音は実際の日本語音声で確認します。
6. 320px相当の画面幅・文字200%・ブラウザ拡大で折り返しと縦スクロールを確認。カウンター通信中と失敗時に開始、Easy/Normal/Hard、サーブ・返球、キーボード、音声、設定、傾き操作、終了を試します。
